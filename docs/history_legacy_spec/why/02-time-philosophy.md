# WHY · 时间系统的设计哲学

> 出处：`History/Utility/HistoryTime.py` 头注释（1-13 行）、`README.md` 最近更新节（51-55 行）与时间日期说明节（96-105 行）、`History/doc/datetime_algorithm.pdf`。

## 为什么自造 TICK 而不是 datetime

`HistoryTime.py:1-6` 的头注释阐明了世界观的二分：

- **TICK 是「真实世界的时间刻度」**——连续、无限、与历法无关；
- **年月日是人为历法**——是投射在 TICK 之上的标签层，二者无必然对应。

datetime 不能承担这个角色，因为：

1. datetime 有范围限制（year 1 ~ 9999），历史时间需要正负无穷（史前到未来）；
2. datetime 没有 0 年，而历史时间轴必须能平滑跨过公元边界；
3. 浮点年份（旧版方案）有精度与进位问题。

TICK 定义为**整数秒**：公元元年（1 AD）1 月 1 日 0 点 = 0，公元后为正、公元前为负，均至无穷。**没有 0 年**：`year = -1` 表示公元前 1 年（1 BC）。

README 最近更新节（51-54 行）确认这是从旧「浮点年份」系统重构而来：「这次更改的程度非常大，程序中时间的使用变得非常严谨」。`History/doc/datetime_algorithm.pdf` 是为该算法（400/100/4 年四级分解、闰年公式）撰写的专题设计文档。

## 公元前的「镜像」处理

头注释 `:5` 声明了一个重要约定：**公元前的月日仅供参考**——公元前一日 = 公元前 1 年 12 月 31 日，公元前二日 = 12 月 30 日，依此从年末倒推。闰年规则对年份取绝对值镜像使用。

理由：远古日期的历法本身就是失真的（历法改革、史料模糊），追求天文学上精确的 BCE 月日没有实际意义；镜像规则保证 TICK 轴连续无跳变即可。这个「不必过分严谨」的态度后来被用户明确确认：迁移时不需要 TICK 的双向精确转换器，自然语言解析「能认出历史文章里复制的时间文字」即可（根目录 `migration_analysis.md` §8.1）。

## 为什么容错优先

README 时间日期说明节（97, 104-105 行）：

> 程序在为了识别各种不同的时间格式上花费了大量精力，通常文章中直接复制下来的时间文字都能顺利识别……总之程序中尽量提高容错度以提供录入的方便。

这解释了解析器里一系列「激进」行为的设计合理性：

- 「约」字被静默删除（近似时间当精确时间）；
- 无关文字被忽略；
- 「世纪」→「00」的粗糙替换（21 世纪 → 2100 年）；
- 无「年」字样的数字段一律当作公元年份。

**容错换准确性是刻意的**：录入场景的痛点是「从文章里复制的时间认不出来」，而不是「误识别」。错误的时间用户会在悬浮提示里看到并纠正。

## 为什么自研解析器而不用 dateutil

`HistoryTime.py:167-168` 的 docstring：

> Why not use dateutil? Because the parse process is hard to control. We have to detect history date.

dateutil 无法控制解析过程（无法识别「公元前」「前 12 世纪」这类历史表达），且不支持公元前。因此自研了管线式解析器（完整规则见 [how/02-natural-language-time-parsing.md](../how/02-natural-language-time-parsing.md)）。

## 对迁移的启示

- UniversalHistory 的 `JDNTimestamp`（微秒定点整数 + 天文纪年 + 外推格里高利历）是 TICK 哲学的**严谨化延续**：同样的「真实刻度 vs 历法标签」二分，但用标准 JDN 消除了自定义零点和镜像规则。
- 「容错优先」是**必须保留**的用户可感知行为，新实现的适配层完整复用了旧解析管线。
- 「公元前月日仅供参考」意味着迁移验收不应要求 BCE 月日的精确一致。
