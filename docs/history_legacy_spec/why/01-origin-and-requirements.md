# WHY · 项目起因与原始需求

> 出处：`History/README.md` 起因节（60-73 行）、设计节（75-84 行）。

## 起因

作者对历史感兴趣，想找一个基于时间线的历史笔记工具。在网上找了一圈，发现现有软件对时间线的处理通常**只能显示单点时间或时间段中的一种**，无法满足需求，于是自研。原话：「人生苦短，还是先 py」——网页版想做但不熟 web 开发，先用 Python/PyQt 实现桌面版。

## 原始需求（8 条）

1. **可本地编辑，离线使用。**
2. **内容可自由扩展**，而不是作者编辑好后大家只读。
3. **支持在一个坐标轴上同时显示事件以及时间段。**
4. **支持坐标轴缩放。** 在不同时间尺度上（万年，世纪，百年，一年，一日）展示适当的内容。
5. **能识别事件描述中的时间、地点、人物、组织、事件**，并以此为索引进行关联查找和浏览。
6. **可以定义多个 filter 并放置在同一个视图下**，如人物、朝代及事件，以方便对照查阅。
7. **多平台浏览编辑以及随身记录。**
8. **布局清晰显示漂亮**——然而上面的功能优先。

## 需求到功能的映射

| 需求 | 衍生的设计 |
| --- | --- |
| 1、2 | 纯文本 .his 本地文件、depot 目录组织、编辑器 |
| 3 | 记录的 `since/until` 双时间点；单点事件与持续事件两种绘制形态 |
| 4 | TICK 无限时间轴、STEP_LIST 刻度档位体系 |
| 5 | 五要素 label、`focus_label`、关联查找 |
| 6 | Thread 体系（时间轴两侧任意多条线索）+ Filter |
| 7 | Index 概念（轻量摘要指向完整内容，为在线场景准备） |

## 使用方式的自我定位

README「参考内容」节（110-112 行）给出了作者预期的使用方式，也是理解界面设计的钥匙：

> 光看这个时间轴对从零开始了解一段历史其实作用并不大，最佳食用方法是**配合优秀文章书籍对照观看**。

即：时间轴是「对照工具」而非「内容源」，这解释了多 Thread 对照为什么是软件的初心（见 [04-rendering-philosophy.md](04-rendering-philosophy.md)），也解释了录入功能为什么追求低摩擦（见 [02-time-philosophy.md](02-time-philosophy.md) 的容错优先）。

## 项目状态的自我评价

README 更新与通知节（13-37 行）中作者自述：

> 我虽然"实现"了一个看起来不错的时间轴，但其机制并非严谨的、标准的。因此进一步的改进也不过是在一个不稳固的地基上堆叠建筑。

这是迁移到 UniversalHistory（JDN 基准 + 外推格里高利历 + 可扩展桥接层）的直接动机，并承诺「数据是可以完全兼容的，现在的软件请放心使用，软件版本的升级并不会带来沉没成本」。
